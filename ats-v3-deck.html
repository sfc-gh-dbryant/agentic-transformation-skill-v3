Solution Overview
What is the Agentic Transformation Skill?
A Snowflake-native framework that turns your Bronze tables into analytics-ready Silver in days
ATS is an AI-powered pipeline framework deployed entirely within your Snowflake account. It uses a coordinated team of Cortex LLM agents to plan, execute, validate, and learn from each transformation — guided by your business rules and schema standards.
Unlike traditional pipeline tools, ATS doesn't just automate SQL execution. It understands your data — discovering relationships, inferring transformation strategies, and capturing learnings that make every subsequent run smarter than the last.
What You Get
  • Silver tables — transformed, validated, analytics-ready
  • Schema contracts — structural rules encoded for repeatability
  • Transformation directives — reusable business rules
  • The ATS framework — deployed in your account for the duration of the engagement
  • Full lineage + audit logs — every decision documented
  • DCM export — production-ready deployment artifacts
What ATS Is Not
Not a Product
ATS is delivered as part of a Snowflake PS engagement — no support contracts, versioned releases, or SLAs beyond engagement terms.
Not a No-Code Tool
ATS accelerates data engineers — it does not replace them. Your team validates outputs, tunes directives, and adapts the framework.
Not an Ingestion Layer
Bronze tables must already exist. ATS focuses on Bronze → Silver transformation and AI-proposed Gold/Analytics DDL.
Not the Nightly Pipeline
ATS authors your pipeline logic. That logic is then operationalized into Tasks, Dynamic Tables, or dbt models that run independently.

Data Safety
Built to Run Safely in Any Environment
Three default safeguards protect existing data — greenfield or brownfield
🔍
Dry Run Mode
Default: ON. Every pipeline run generates and logs DDL but executes nothing. Your team reviews every statement before a single table is touched. Execution requires explicit opt-in.
🛡️
Overwrite Protection
Default: OFF. If a target table already has rows, the Executor skips it, logs it, and continues. Existing data is never overwritten unless explicitly permitted — and only after dry run is also disabled.
🌾
Brownfield Mode
Skip-and-log. For environments with existing Silver tables, Brownfield Mode skips those tables entirely and processes only the gaps. Existing tables are logged as EXISTING and left untouched.
Default behavior guarantee
A first run against any environment — greenfield or brownfield — produces zero side effects until your team has reviewed and approved the proposed DDL. No surprises, no accidents.
Conflict Handling
When a target table conflict is detected, ATS automatically routes output to a staging schema (OUTPUT_SCHEMA_STAGING) for review — no data loss, no pipeline failure, full audit trail.
Audit Trail
Every decision — every generated DDL, every LLM plan, every validation result — is logged to WORKFLOW_LOG with timestamps, phases, and execution IDs. Full reproducibility guaranteed.

Partner Routing
Multi-Banner Partner Routing
One Silver table → multiple Gold tables, routed by banner, region, store format, or any dimension value
Many enterprise customers have a fan-out pattern at the Gold layer: a single Silver product catalog routes to separate Gold tables per business unit, region, or store format — each with its own filtering rules, exclusions, and merge targets.
ATS v3's Partner Routing module handles this natively. Configure once, validate against Silver, generate Gold-per-banner DDL ready for DCM export.
Routing Capabilities
  • Banner-level Silver filters — WHERE BANNER = 'superstore'
  • Exclusion accounting — Gold = Silver minus excluded categories (validates correctly when Gold < Silver)
  • Merge targets — route minority banners into a shared Gold table
  • Configurable thresholds — per-partner UPC variance tolerance
  • Validation suite — full banner-level row count comparison before Gold build
Example: Large Grocery Retailer (14 banners → 13 Gold tables)

icmBANNER = 'icm'→ GOLD_INDEPENDENT (merge)

Use Case
Real-World Scenario: Multi-Business-Unit Migration
The ATS pattern applied to a complex, multi-BU migration with legacy schemas and undocumented logic
The Situation
An enterprise is migrating 12–20 business units from on-premises SQL Server and legacy ETL to Snowflake. Each BU brings raw Bronze tables — claims, premiums, policy data — with legacy schemas, inconsistent NULLs, undocumented PKs, and transformation logic embedded in SSIS packages nobody fully understands.
Traditional Approach
  • Data engineer manually reverse-engineers each BU's schema
  • Writes Silver DDL by hand — weeks per business unit
  • Validation scripts written from scratch per table
  • No knowledge transfer between BUs — BU 12 starts from zero
  • 4–8 weeks per BU × 20 BUs = up to 2+ years
With ATS
  • Configure pipeline context once: domain, output schema, contracts
  • Add directives for known edge cases per BU
  • Agents plan and execute Silver transformation in days
  • Reflector learnings from BU 1 inform BU 2's execution automatically
  • Pattern repeats across all 20 BUs at a fraction of the time and cost
"When the next business unit onboards, the framework already knows the domain. The Reflector's learnings from BU 1 inform BU 2's execution. The pattern repeats across all business units at a fraction of the cost and time of manual development."
